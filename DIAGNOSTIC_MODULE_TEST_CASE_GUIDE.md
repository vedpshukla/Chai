# Diagnostic Module FHIR R4 test-case guide

## Purpose

This document explains how to use [diagnostic_module_fhir_r4_test_cases.csv](diagnostic_module_fhir_r4_test_cases.csv) with synthetic patient records generated by [Synthea](https://github.com/synthetichealth/synthea).

The CSV is the test contract. Each row says:

- which FHIR resource and operation to call
- whether the case is positive or negative
- what synthetic input is needed
- which HTTP status should be expected
- what must be checked in the response
- which FHIR R4 rule or project rule is being tested

No real patient information should be used.

## Scope confirmed from this repository

The current project registry supports these Diagnostic Module resource types:

- `Observation`
- `DiagnosticReport`
- `ServiceRequest`
- `DocumentReference`
- `ImagingStudy`
- `Bundle` for batch and transaction processing

The route prefix registered by the application is:

```text
/exlinterop/v1
```

The implementation is JSON-only at this stage. Use:

```text
Content-Type: application/fhir+json
```

`application/json` is also accepted by the parser. XML is a valid FHIR R4 representation in the standard, but this project currently rejects XML with `415`.

## How to use the CSV

### 1. Select a test row

Start with the `test_id` column. For example:

```text
DM-OBS-P-001
```

### 2. Generate synthetic patient data with Synthea

Synthea is a synthetic patient population simulator. It can generate realistic, non-production patient records and export them in FHIR R4 format. Synthea requires Java JDK 17 or newer.

From a separate folder, download and build Synthea:

```powershell
git clone https://github.com/synthetichealth/synthea.git
Set-Location synthea
./gradlew.bat build
```

Generate a small deterministic population and enable FHIR output:

```powershell
./run_synthea.bat -s 12345 -p 10 --exporter.fhir.export=true --exporter.baseDirectory="./output_fhir"
```

Synthea normally writes FHIR records below its output directory. Use the generated FHIR R4 JSON as the positive test-data source. Keep the seed and population size recorded with the test run so the data can be reproduced.

Synthea should generate only non-production values for placeholders such as:

- `{patient_id}`: a simple synthetic id such as `syn-patient-001`
- `{observation_id}`: the id returned by a previous create call
- `{observation_datetime}`: a valid ISO 8601 date-time ending in `Z`
- `{study_uid}`, `{series_uid}`, `{instance_uid}`: numeric-only synthetic DICOM UID fragments
- `{document_id}`: a synthetic document key

The Synthea record may be a complete patient Bundle or a collection of individual FHIR resources. Extract the required resource from the Synthea output before sending it to the resource endpoint. Do not send a patient Bundle to an `Observation`, `DiagnosticReport`, `ServiceRequest`, `DocumentReference`, or `ImagingStudy` endpoint.

Synthea does not need to produce every negative case directly. For negative rows, start with a valid Synthea resource and apply one controlled mutation, such as changing `Observation.status` to `bogus`, removing `Observation.code`, adding an unknown property, or adding both `valueString` and `dataAbsentReason`. Keep the mutation documented against the CSV row and do not apply additional changes that could create an unrelated failure.

The generator or extraction step must preserve the FHIR JSON structure. It may change synthetic values, but it must not remove fields required by the selected positive test or silently remove the intended negative condition.

### 3. Replace placeholders

Replace the placeholders in `synthetic_input_template` and `endpoint` before sending the request.

For example:

```text
{patient_id} -> syn-patient-001
{effective_datetime} -> 2026-09-09T10:00:00Z
```

### 4. Add authentication headers

The normal test header set is:

```text
Client: testclient
Authorization: Bearer <valid-token>
Content-Type: application/fhir+json
```

The token and client must be accepted by the test environment. Do not put real credentials in the CSV or in generated test artifacts.

### 5. Send the request

For a Windows PowerShell example:

```powershell
$body = Get-Content .\payload.json -Raw
Invoke-RestMethod `
  -Method Post `
  -Uri http://localhost:8080/exlinterop/v1/Observation `
  -Headers @{ Client = 'testclient'; Authorization = 'Bearer <valid-token>' } `
  -ContentType 'application/fhir+json' `
  -Body $body
```

For negative cases, do not stop when an error is returned. The error is the expected result. Compare it with `expected_http_status` and `expected_response_checks`.

## Reading expected status values

Some positive create cases say `201 DB or 202 spool`.

- `201` means the resource was persisted in MongoDB.
- `202` means MongoDB was unavailable and the project accepted the resource into the spool directory.
- A `202` response is not the same as a confirmed database write.

For negative validation cases:

- `400` means the request cannot be parsed or fails basic structure/type checks.
- `401` means authentication failed.
- `404` means the resource or supported endpoint was not found.
- `409` means a duplicate or conflict was detected.
- `415` means the request content type is unsupported.
- `422` means the resource structure was readable but a FHIR value binding, invariant, or project business rule failed.
- `503` means an operation requiring storage could not be completed because storage was unavailable.

FHIR failures should normally contain an `OperationOutcome` with at least one `issue`. The issue should have a severity, code, and useful diagnostic text.

## Recommended execution order

Run the tests in this order so later tests can reuse ids returned by earlier tests:

1. `DM-OBS-P-001` create an Observation.
2. `DM-DR-P-001`, `DM-SR-P-001`, `DM-DOC-P-001`, and `DM-IMG-P-001` create the other supported resources.
3. `DM-OBS-P-004` read the Observation.
4. `DM-OBS-P-005`, `DM-OBS-P-006`, and `DM-OBS-P-007` search it.
5. `DM-OBS-P-008` update it.
6. `DM-OBS-P-009` and `DM-OBS-P-010` check history and version read.
7. `DM-OBS-P-011` delete it.
8. Run the negative tests.
9. Run the batch and transaction tests.

For `DM-OBS-N-013`, create the original Observation first and submit the same business key again. This case requires Mongo mode because the duplicate lookup needs a database collection.

## Resource-specific test coverage

### Observation

The CSV covers:

- valid final results
- value quantity and absent result patterns
- status and code required fields
- invalid status
- unknown property
- resource type mismatch
- malformed and empty body
- wrong content type
- `obs-6`
- `obs-7`
- create, read, search, update, history, vread, delete
- duplicate business key

FHIR R4 facts used here:

- `status` is required.
- `code` is required.
- `value[x]` is a choice element.
- `dataAbsentReason` cannot be sent with `value[x]` under `obs-6`.
- If `Observation.code` matches a component code, the value is disallowed under `obs-7`.

### DiagnosticReport

The CSV covers:

- valid final report
- result Observation references
- ImagingStudy references
- invalid and missing status/code behavior

FHIR R4 facts used here:

- `status` is required.
- `code` is required.
- `result` references Observation resources.
- `imagingStudy` references ImagingStudy resources.

### ServiceRequest

The CSV covers:

- active order
- status values
- intent values
- patient subject
- missing subject

FHIR R4 facts used here:

- `status`, `intent`, and `subject` are required.
- `code` is optional in base R4.
- `intent` and `status` use required value sets.

### DocumentReference

The CSV covers:

- current document with PDF metadata
- invalid status
- missing content

FHIR R4 facts used here:

- `status` is required.
- `content` is required and repeats one or more times.
- The attachment can point to a URL or carry data, depending on the use case.

### ImagingStudy

The CSV covers:

- available study
- synthetic DICOM study/series/instance identifiers
- invalid status
- missing subject

FHIR R4 facts used here:

- `status` is required.
- `subject` is required.
- ImagingStudy describes a DICOM study; it does not itself store the image bytes.

## Search coverage and important limitation

FHIR R4 defines many search parameters. This project registry currently maps only these common search keys:

```text
_id
identifier
status
subject
patient
code
```

The CSV therefore tests the search behavior that this repository currently advertises through its registry. It does not claim that all standard FHIR R4 search parameters are implemented.

FHIR search responses should be checked for:

- HTTP `200`
- `resourceType` equal to `Bundle`
- `type` equal to `searchset`
- correct `total` when supplied
- `entry.search.mode` equal to `match` for matched resources
- the response `link[relation=self]` when the server supplies it

## Batch and transaction checks

FHIR R4 treats these differently:

- A `batch` processes entries independently. The overall response is normally `200`, and each entry reports its own status.
- A `transaction` is atomic. If one entry fails, the entire transaction is rejected.

The project’s expected behavior is represented by:

- `DM-BUNDLE-P-001`
- `DM-BUNDLE-P-002`
- `DM-BUNDLE-N-001`
- `DM-BUNDLE-N-002`

## Minimum automated checker behavior

A runner consuming the CSV should perform these checks:

1. Parse each CSV row.
2. Generate or load Synthea FHIR R4 resources.
3. Substitute placeholders without changing the intended positive/negative condition.
4. Send the HTTP request.
5. Compare the actual status with the allowed status expression.
6. Parse JSON responses when a body is expected.
7. For failures, require `resourceType=OperationOutcome` and at least one `issue`.
8. Check exact fields listed in `expected_response_checks`.
9. Save request and response evidence with the `test_id`.
10. Never save real PHI in evidence files.

A result should be reported as `PASS` only when both the HTTP status and the response assertions pass.
