The shape of it

Three bands. The transport edge (Flask) does only what needs a request object: auth, tracking, and shaping the HTTP response. The pipeline (fhirpipeline/) takes plain bytes and returns a plain dataclass — it never imports Flask. The store (persist.py) is handed an injected collection accessor, so it has no DB driver at import time.

A single resource and a Bundle enter through different routes but share one core: ingest() detects the shape, and a Bundle entry is validated by the exact code a lone POST uses. Every failure — anywhere — leaves as an OperationOutcome with the right HTTP status.

Convert first, then validate. Steps 2–4 turn whatever arrived into canonical FHIR JSON (spec fields only, correct primitive types, ISO dates, no nulls). Everything from step 5 onward works on that one predictable shape.

Full flow diagram

Markers 1–9 run top to bottom. Teal markers are the transport edge; the rest is the Flask-free pipeline and store. Red chips are failure exits — the response status returned if that step rejects.

  1. 1
    Route & auth routes/common/auth.py · resource_common.py / bundle_common.py

    Blueprint matches POST /Observation or POST /Bundle. validate_auth_request() checks the Client header + Bearer JWT → (clientname, payload). A tracking record is opened.

    ValueError → 401 security
  2. 2
    parse fhirpipeline/parse.py

    Raw body bytes + Content-Type → a JSON dict guaranteed to carry a non-empty resourceType. Missing Content-Type → a warning, not a failure.

    non-JSON → 415 not-supported empty → 400 required bad JSON / no resourceType → 400 structure
  3. 3
    registry lookup fhirpipeline/registry.py

    get_spec(resourceType) → a ResourceSpec (collection, required fields, value sets, invariants, duplicate key, search params) or None. Data, not logic — consumed by steps 4–8.

    no spec → 404 not-supported
  4. 4
    dispatch — one path per shape fhirpipeline/dispatch.py

    Branch on resourceType. Both branches run the same steps 5–6.

    single

    dispatch_single(): check the URL hint matches the body, then steps 5–6 once.

    Bundle

    dispatch_bundle(): validate the envelope (type ∈ transaction / batch / collection), then run every entry.resource through steps 5–6. Per-entry failures are captured, not raised. transaction = all-or-nothing.

    body vs URL mismatch → 400 processing bad Bundle.type → 400 structure
  5. 5
    canonicalize fhirpipeline/canonicalize.py

    construct_fhir_element(rt, dict) via fhir.resources R4B. On success, re-serialise with model.json(exclude_none=True) → canonical JSON. Unknown fields, wrong primitive types, and bad date formats fail here.

    doesn't construct → 400 structure (one issue per bad field)
  6. 6
    validate fhirpipeline/validate.py + invariants/observation.py

    On the canonical dict: required elements, value-set bindings (status, intent, … — the checks fhir.resources does not do), and cross-element invariants (obs-6, obs-7, has-a-result). All problems accumulated so the client sees them at once.

    any error-severity issue → 422 invariant warnings → carried on the response
  7. 7
    assemble — IngestResult fhirpipeline/pipeline.py

    ingest() never raises. Success → IngestResult(ok=True, kind="single"|"bundle", canonical|bundle, warnings). Any PipelineError → ok=False + outcome + status. A rejected transaction → ok=False, 400, one issue per failed entry.

    unexpected Exception → 500 exception (detail to logs only) ok → hand to persist
  8. 8
    persist — append-only fhirpipeline/persist.py

    Injected get_collection(client, name) → collection | None. create: assign id + meta.versionId "1", dedup (ResourceId → identifier → business key), insert row. update: flip old row IsCurrent → 0, insert v+1. delete: flip + insert a tombstone. Bundle: persist_bundle loops this per entry.

    duplicate → 409 target missing → 404 DB down + delete → 503 DB down + write → 202 spooled to file 201 / 200 / 204
  9. 9
    Transport response resource_common.py / bundle_common.py

    single: body is the stored resource (or the OperationOutcome), plus Location and ETag: W/"<versionId>". Bundle: a <type>-response Bundle, one entry per request entry with its own response.status / location / outcome. Tracking record finalised.

    unhandled → 500 OperationOutcome, traceback to logs

AExample — POST /Observation, DB up, valid

1 route+auth Client + Bearer JWT ok → clientname="lab-a"
2 parse body is a dict, resourceType="Observation" → (dict, [])
3 registry get_spec("Observation") → ResourceSpec(collection="Observation", …)
4 dispatch hint "Observation" == body → dispatch_single
5 canonical construct_fhir_element ok → canonical JSON (nulls dropped, dates ISO)
6 validate status "final" ∈ set · code present · obs-6/obs-7 ok → warnings=[]
7 assemble IngestResult(ok=True, kind="single", canonical=…)
8 persist create: id=uuid4, meta.versionId="1"; no duplicate; insert row IsCurrent=1
9 response 201 Created Location: Observation/<id>/_history/1 ETag: W/"1"

BExample — POST /Bundle transaction, one bad entry

entry[0] a valid Observation; entry[1] an Observation with status: "bogus".

1 route+auth ok → clientname="lab-a"
2 parse resourceType="Bundle" → (dict, [])
4 dispatch Bundle.type="transaction" ok → dispatch_bundle
  entry[0] → dispatch_single → 5 canonical ok → 6 validate ok → EntryResult(ok=True)
  entry[1] → dispatch_single → 6 validate: "bogus" ∉ status value set
          ValidationFailed caught → EntryResult(ok=False, issues=[…])
7 assemble any_error & type==transaction → rejected
          IngestResult(ok=False, status=400, outcome=_bundle_outcome)
9 response 400 Bad Request OperationOutcome — one issue per failed entry, tagged Bundle.entry[1]
nothing persisted

Swap type to batch and the same input returns 200 with a batch-response Bundle: entry[0] at 201, entry[1] at 400. Batch tolerates partial; transaction does not.

Where to change things

A new resource type

Add one RESOURCE_REGISTRY entry in registry.py (collection, required fields, value sets, optional duplicate_key_fn, search params). Optionally a module under invariants/ for cross-element rules. Then a one-line blueprint: make_resource_blueprint('NewType'). Steps 2–9 pick it up unchanged.

A new module

Its resource files each call make_resource_blueprint(...); one file calls make_bundle_blueprint('ModuleName'). Auth, ingest, persist, and search are all shared — nothing in fhirpipeline/ changes.

Phase 2 — XML input

A single branch in parse.py (step 2): detect XML, transcode to a JSON dict, return it. Steps 3–9 are already JSON-only by contract, so they do not change. The internal canonical form stays FHIR JSON.
